# EarthScope — Product Design Specification

## 1. Project Overview

EarthScope is a browser-based earthquake monitoring, visualization, and geophysical analysis application.

Its purpose is to provide an integrated environment for exploring earthquake activity, seismic intensity, hypocenter distributions, geological structures, and eventually seismic waveforms and Earth interior models.

EarthScope is designed primarily as a static web application hosted on GitHub Pages. It must not assume the existence of a dedicated backend.

The project prioritizes:

- Scientific accuracy
- Data provenance and transparency
- Reliable visualization
- Extensible architecture
- Performance on ordinary desktop computers
- Clear distinction between observed and derived information

EarthScope is not intended to imitate a simple earthquake notification dashboard. It is intended to grow into a comprehensive geophysical visualization platform.

## 2. Core Principles

### 2.1 Scientific integrity

Every displayed dataset must have identifiable provenance.

The application must distinguish:

- `OBSERVED`: Directly observed or published measurement
- `CALCULATED`: Computed from available data using a documented method
- `ESTIMATED`: Estimated from incomplete or indirect information
- `SIMULATED`: Generated by a simulation
- `MODEL`: Derived from a scientific model
- `ILLUSTRATIVE`: Explanatory visualization without quantitative scientific validity
- `UNAVAILABLE`: Data that cannot currently be obtained

Do not present calculated, estimated, simulated, or illustrative values as direct observations.

### 2.2 Static-first architecture

The primary application must work as a static frontend.

Do not require:

- A custom API server
- A database server
- Server-side rendering
- Persistent backend storage
- A proprietary data relay

External APIs may be used when their access conditions permit browser-side requests.

If a data source requires authentication, a server-side proxy, or restricted redistribution, do not bypass those restrictions.

### 2.3 Graceful degradation

Failure of one data source must not prevent the application from displaying information from other sources.

Every data provider must have:

- Loading state
- Success state
- Error state
- Last successful update timestamp
- Retry capability where appropriate
- Clear source attribution

## 3. Application Scope

### Core features

- Earthquake catalog
- Earthquake search and filtering
- Interactive earthquake map
- Magnitude, depth, and time visualization
- Earthquake detail panel
- Seismic intensity display
- Basic statistics
- Data source and update status

### Intermediate features

- Cross-section visualization
- Hypocenter distribution analysis
- Magnitude-frequency distribution
- b-value calculation
- Spatial and temporal analysis
- Selected-event prefecture-level intensity distribution
- Geological and plate boundary overlays

### Advanced features

- Japan-limited 3D crust block
- Earth interior visualization
- Seismic waveform display (user-provided CSV/JSON)
- Focal mechanism visualization
- Tomography and velocity models
- Strong-motion analysis
- Click-to-select hypocenters in the 3D block

Advanced features must be implemented only when appropriate datasets and usage permissions are available.

## 4. Data Source Strategy

### 4.1 USGS

USGS earthquake feeds are the primary source for an initial automatically updating global earthquake catalog.

Use official GeoJSON feeds where possible.

The frontend should:

- Fetch the selected feed periodically
- Avoid unnecessary repeated requests
- Preserve the original source event ID
- Display the source update timestamp
- Handle duplicate and revised events
- Distinguish event time from feed update time

### 4.2 Japan Meteorological Agency

JMA earthquake information is a preferred source for domestic earthquake information.

However, browser access must be verified for each endpoint.

Do not assume that an endpoint supports CORS merely because it is publicly accessible.

JMA disaster-prevention XML is a pull-based service. The previous push environment ended on 2020-09-01.

Polling may be implemented only after endpoint availability, access conditions, update frequency, and request limits have been checked.

### 4.3 NIED

NIED datasets must be handled individually.

Do not assume that all NIED datasets are freely downloadable or redistributable.

For each dataset, document:

- Registration requirements
- Authentication requirements
- Redistribution restrictions
- Citation requirements
- Browser accessibility
- Data format
- Intended use

Hi-net waveform access and K-NET/KiK-net waveform access must not be treated as unrestricted public APIs.

### 4.4 Other datasets

Potential sources include:

- J-SHIS
- F-net
- Geological Survey of Japan
- Published plate models
- Published seismic velocity models
- USGS geological datasets

Each source must be reviewed before implementation.

## 5. User Interface

The interface should prioritize information density and usability.

Avoid unnecessary:

- Glow effects
- Excessive gradients
- Glassmorphism
- Decorative animations
- Oversized headings
- AI-generated explanatory filler

Use a consistent visual hierarchy.

The application should provide:

- A main map or visualization area
- A compact event list
- A detailed event information panel
- Time and magnitude filters
- Data source status
- Optional analysis panels

The layout must remain usable on smaller screens, although desktop is the primary target.

## 6. Map and 3D Visualization

MapLibre GL JS is the primary geographic map renderer.

Three.js is used for the Japan-limited, non-spherical 3D crust block. A global Earth globe is not part of the current scope.

The application must account for the fact that both systems use WebGL.

Use lazy initialization, renderer disposal, resource cleanup, and WebGL context-loss handling.

Do not assume a fixed browser WebGL context limit.

The initial 3D camera orientation must be explicitly defined. The initial view centers the operational Japan region on the crust block.

Right-drag orbits, middle-drag pans, and the wheel zooms. The 2D GSI map remains visible; the 3D block is an optional section in the 地震分布図 panel, enabled only when Slab2 is on. The 3D renderer is lazy-mounted and disposed when hidden.

## 7. Performance

- Use Web Workers for expensive calculations.
- Avoid unnecessary React re-renders.
- Use Float64 for coordinate calculations requiring high precision.
- Use Float32 for suitable GPU-oriented scientific datasets.
- Use lazy loading for advanced visualization modules.
- Dispose unused GPU resources.
- Avoid loading large waveform or tomography datasets before they are requested.

## 8. Development Philosophy

Implement a working and scientifically valid core before adding advanced features.

A feature is not complete merely because it can be visually displayed.

It must also have:

- A documented data source
- A documented calculation method
- Correct units
- Correct coordinate handling
- Error handling
- Appropriate uncertainty disclosure
- Tests for important calculations

The long-term vision is comprehensive geophysical analysis, but the application must remain useful even when restricted datasets are unavailable.
